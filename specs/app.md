# App

**Status:** Updated

> **Code layout.** `system.py` holds the **wiring + lifecycle** of one session (`build_system`, the `AppSystem` snapshot, `wire`, `open_session`, `close_session`) and the command line (`run_app`); `session.py` the session that starts and stops again ([session.md](session.md)); `app_ui.py` the **Gradio presentation layer** (the `display_entry` hook, `build_page`, the session's surfaces, the ASR/Vision live views its timers poll); each embodiment's `app.py` declares its app ([setup.md](setup.md)) and has a `main()` of a few lines calling `run_app`. The three framework-observability panels — Conversation, World state, Reaction — are WICA's reusable `wica.contrib.gradio` components (the `wica[gradio]` extra — `wica-framework/specs/gradio-contrib.md`), and the Setup and Secrets tabs are app-setup's panels (`app-setup/specs/ui.md`), all placed by `build_page`. `system` imports nothing from `app_ui`; `app_ui` depends on `system` and `session` for their types, so there is no import cycle.

## Purpose

The runnable **interaction application**: a Gradio UI, modeled on WICA's conversation demo (`wica-framework/specs/conversation-demo.md`), in which a person **speaks** to a WICA agent and the agent **speaks (and, embodied in a robot, acts) back**. It wires speech-in ([asr-bridge.md](asr-bridge.md)), vision-in ([gesture-input.md](gesture-input.md)) and an **embodiment** ([embodiment.md](embodiment.md) — the computer's mic/speakers/webcam, or the Reachy Mini) around a WICA agent, and shows the demo's *observability* panels (Conversation / World / Reaction, reused from `wica.contrib.gradio`) plus a live **ASR panel** of its own. Everything is stood up from the [config](configuration.md) of the app's folder, edited, checked and completed from the page's Setup tab ([setup.md](setup.md)); the runtime is a **session** the page starts and stops ([session.md](session.md)).

This is the app the WICA demo only *simulated*: there, "speech in" was a text box and "speech out" a fake word-by-word reveal. Here they are a real microphone and real audio — and, on the robot, the agent can move.

## Data flow

```
embodiment.mic ─▶ ASREngine ─▶ AsrBridge._on_segment
                      │  interim ─▶ ASR panel (live text)         [agent NOT triggered]
                      └─ final ──▶ world.update("speech_input") ──▶ WICA Agent reasons
typed text ─▶ strip, drop empty ─▶ world.update("speech_input") ──▶  │  ├─ <say>…</say> ─▶ embodiment.voice ─▶ speakers / robot
embodiment.camera ─▶ GestureInput ─ (hand, sign/None) on change ─▶ world.update("hand_gesture_<n>") ─┤  (triggered when a sign is shown)
embodiment.inputs() ─▶ each producer ─ deliver(key, value) ─▶ world.update(<its own entry>) ──────────┤  (as its entries say: the robot's users)
                                                                     │  ├─ embodiment.commands() ─▶ e.g. play_emotion ─▶ robot
                                                                     └─ text outside the tag ─▶ private (💭 thought, in the transcript)
```

- **Speech in.** A closed ASR segment is written to the World's `speech_input` entry, which triggers one reasoning step. **Every** closed segment is written verbatim — including an empty/whitespace one (a passage that closed on silence), so the agent can react to the person saying nothing ([asr-bridge.md](asr-bridge.md)). Interim speech only updates the ASR panel. Typed text makes the same World update, minus empty lines (see "The input funnel"). The utterance is **transient**: 2 s after it lands the World clears it and it is gone from every later prompt (see "Inputs are transient").
- **Vision in.** The embodiment's camera runs through `vision-modules`' hand + gesture pipeline; `GestureInput` reduces each published hand to a sign (`stop`, `like`, `dislike`, `ok`, `one` … `five`) or `None`, holds it (a sign for `vision.hold_s`, 0.3 s by default; a sign going away for `vision.release_hold_s`, 0.5 s) so a flicker never counts, and writes that hand's `hand_gesture_<n>` entry **on change only**; the entries' trigger predicate wakes the agent whenever a hand shows a sign, riding the normal coalescing window ([gesture-input.md](gesture-input.md)). A sign is transient too: the World clears it 1 s after it lands.
- **The body's own perceptions.** An embodiment may perceive on its own and say so through `inputs()` ([embodiment.md](embodiment.md), "`inputs()` is the mirror of `commands()`"): each input brings the World entries it writes and a producer this app starts once the agent runs, handing it a guarded `deliver`. The robot's is its users: who arrives and leaves, who is present, who is in its personal space, and whom its head follows ([reachy-embodiment.md](reachy-embodiment.md), "Users: `UsersInput`"). The computer has none.
- **Reason.** The WICA Agent renders the World into a prompt, runs inference, and acts.
- **Speech out.** The agent speaks by writing a `<say>…</say>` tag in its response text: the tag is named after the **output Command**, the embodiment's `voice`, which WICA calls at the tag's first words with a stream of its body, so the voice speaks while the model is still writing. The output Command is not a tool; each tag is its own tracked execution (an `agent:command:<call_id>` entry, `running` while the speech plays). A response that speaks cuts off speech still running from an earlier one; other Commands are left alone. The end of the speech wakes no step unless the response carried a `<next>` note. Text the model writes outside the tag is private reasoning, never heard: WICA reports it on `on_agent_private_text`, which the transcript presenter subscribes to, so it shows in the Conversation as a 💭 item (`wica-framework/specs/agent.md`, "Output: tags in the model's text").
- **Act.** The agent can call whatever Commands the embodiment registers — on the robot `play_emotion` / `set_motors_state` / `get_motors_state` ([reachy-embodiment.md](reachy-embodiment.md)); on the computer none.
- **Dictation.** On request the agent calls `start_dictation` to capture a longer passage as one `speech_input` ([asr-bridge.md](asr-bridge.md)).

## World, Commands, persona

- **World entries:** `speech_input` (the triggering input), `hand_gesture_1` … `hand_gesture_<max_hands>` (the sign a hand just showed, registered only when vision is on), the embodiment's own entries, registered from its `inputs()` (on the robot, `user_event`, `users_in_view`, `personal_space` and `tracked_user` — [reachy-embodiment.md](reachy-embodiment.md)), and the automatic `agent:command:*` entries WICA tracks for in-flight Commands. The app's two inputs are one-shot observations (below), and so is every event an embodiment adds; a state an embodiment adds may wake the agent when it changes (the robot's `personal_space`).
- **Standing entries, by exception.** The World mirrors no embodiment state — the motors, the camera frame, the head's pose are not entries — with one exception: the robot's users, as three entries, one per concept: who is present (`users_in_view`), who is inside the personal space (`personal_space`) and whom the head follows (`tracked_user`). None has a TTL, and each is rewritten only when its value changes. They are there because the agent holds the tracking Commands: to follow user 3 it must know, in the step where it decides, that user 3 is present and whom it follows already, which a one-shot event read from history cannot say; and an arrival whose trigger was dropped while a step was in flight is still visible in them. Any further standing entry needs the same case made.
- **Commands:** `start_dictation` / `stop_dictation` ([asr-bridge.md](asr-bridge.md)), the embodiment's own action Commands, plus WICA's auto-registered `cancel_command`. The output Command, `say` (the embodiment's voice), is not among them: it is written as a tag, not called, and doing nothing is the `<noop/>` tag, not a Command.
- **Persona:** whatever the config's `system_prompt_file` says — one file per embodiment (`computer.md`, `reachy.md`: shipped in the embodiment's package and copied into the app's folder, where it is edited — [setup.md](setup.md)), each knowing it speaks by writing a `<say>` tag and that text outside it is never heard, may choose not to react, and can switch to dictation when asked (and that an empty dictated passage means the person paused). Both carry the same **self-knowledge rules** ("What you can do, and what you know"): the agent can do only what its Commands do — a request none of them covers is declined out loud, never pretended — and knows what it is doing only from the Commands it called, their results and the World, so it never claims an action (following a user, dictation) that none of them shows. Prompt rules, not guards. The robot persona adds how it moves and the action rules its colliding Commands need ([reachy-embodiment.md](reachy-embodiment.md), "Persona"). Two sections are **appended as a session is built**, not written in the file: the embodiment's `prompt_addendum` (the robot's emotion names) and, when vision is on, the "Hand signs" section from [gesture-input.md](gesture-input.md) — so a persona never describes hands it cannot see or emotions it cannot play.

### Inputs are transient

Both inputs are **one-shot perceptions**, not standing state: the person *said* something, a hand *showed* a sign. WICA renders the whole World into every step (`wica-framework/specs/agent.md`, "History"), so without care a step woken by something else — a `say` finishing, a command completing, a sign — would re-read the last utterance as if it were current, and a sign would read as held long after the hand relaxed. Two World mechanisms (`wica-framework/specs/world.md`) make each input observed once and then gone, with no app-side bookkeeping:

- **A TTL on each entry.** `speech_input` is registered with `ttl=SPEECH_INPUT_TTL` (**2 s**) and each `hand_gesture_<n>` with `ttl=HAND_GESTURE_TTL` (**1 s**), both module constants in `system.py`. The World resets the value to `None` that long after the update that set it — a reset that advances the entry's `id`, dispatches listeners (the World panel shows it clear) but **never triggers a step**. The step the input triggers observes it well within that window (the coalescing window is ~200 ms); a step started later does not.
- **`None` renders nothing.** Both `serialize_fn`s return an empty `Content` for `None` — nothing said yet or the utterance expired; no sign delivered yet, the hand dropped, or the sign expired — and WICA **omits** such an entry from the render, envelope included ("Omitting an entry" in world.md). So a prompt carries a `speech_input` block only in the step the utterance triggered, and a `hand_gesture_<n>` block only while that hand's sign is live; there is no "hasn't said anything" or "not showing a sign" placeholder. History keeps what was observed (each observation is its own snapshot), so the model still sees earlier utterances and signs in context, just not as current.

**What the prompt says.** Each line says what the app *perceived*, never more than the input knows: the mic cannot tell the person in front of the app from anyone else in the room, nor the camera whose hand it sees, and a wording that claimed it would be contradicted the moment it was wrong — the app hearing its own voice, a hand at the edge of the frame.

| Entry, value | Rendered |
|---|---|
| `speech_input`, an utterance (typed lines included) | `You hear someone say: "<text>"` |
| `speech_input`, a `DictatedPassage` ([asr-bridge.md](asr-bridge.md)) | `Dictation is over. You heard this complete dictated passage: "<text>"` |
| `hand_gesture_<n>`, a sign | `Hand gesture detected on hand <n>: "<sign>".` |
| either, `None` | nothing |

The dictated passage says the dictation is over because the model otherwise read it as one more sentence of the note it had asked for.

An embodiment's entries follow the same rule — what was perceived, never more — in wordings that live with the embodiment that perceives ([reachy-embodiment.md](reachy-embodiment.md), "Users: `UsersInput`": a user *came into view*, never *the same person* or a name).

Two consequences are accepted by design: an utterance whose trigger was dropped because a step was in flight (`wica-framework/specs/agent.md`, "Concurrency") is lost unless a step observes it within 2 s (before, it lingered until the next unrelated step and was then answered late); and a sign the person keeps holding reads as no sign after 1 s until the hand changes, since `GestureInput` delivers changes only and never refreshes an unchanged value.

## What the user sees

Four tabs: **Interaction**, **Latency**, **Setup**, **Secrets**. The first two are this app's and show the session; the last two are app-setup's panels (`setup_panel(model)`, `secrets_panel(model, setup.draft)` — `app-setup/specs/ui.md`), where every section of the config is edited, checked, installed, prepared and tested, and the keys are kept. The page is named after the app — title and heading from `App.title` (`WICA Interaction — Computer`, `WICA Interaction — Reachy Mini`, [setup.md](setup.md)) — whether or not a session runs. It opens on **Interaction** when the session started at launch, else on **Setup** ([session.md](session.md), "Autostart").

**The session bar**, at the top of the Interaction tab, always there:

- **The status line**: `Stopped`, `Starting…`, `Running` or `Stopping…`.
- **Start** and **Stop**, greyed by the status: Start only while stopped, Stop only while running, both greyed while a click is being served. The bar is refreshed on a 1 s timer, so a second browser tab follows the first.
- **Why the last Start did not start**, when it did not: the config's problems and what the machine is missing (`Session.reasons`), each on a line, with "Fix them on the Setup tab, then Start." They stay until a Start that runs.
- **"The Setup tab has unsaved changes: Start uses the saved config."** while the Setup tab's draft differs from the saved config (`app_setup.ui.unsaved_notice`).

**The session's surfaces** — everything below the bar on the Interaction tab, and the whole Latency tab — are drawn in a `gr.render` keyed on `Session.version`, so they are drawn again at each start and each stop, over that session's own objects: its presenters, its World, its collector, its body. While no session runs, their place holds one line saying so. Inside a running session, five panels: three are WICA's reusable observability components from `wica.contrib.gradio` — each a **presenter** built over the `Wica` (subscribing to the instrumentation Events in its constructor, once per session — [session.md](session.md), "The object") plus a **panel** function called inside the render that creates the components and owns the `gr.Timer` keeping them live; the camera, **ASR** and **Vision** are the app's own. **Conversation**, the camera, **ASR** and **Vision** are the *main* surface; **World state** and **Reaction** are *debug* surfaces, hidden by default behind a **"Show debug panels"** toggle — view-only state.

**The layout of a running session.** **Interaction**, under the session bar, top to bottom: the banner; the intro; full width, the **Latency** glance line and live timeline; then the main surface in two rows of two columns of equal width — **Conversation** on the left and, on the right, the body's **camera** with the typed-text box under it; then **ASR** on the left and **Vision** on the right; last, the **"Show debug panels"** toggle, and under it, hidden until ticked, **World state** and **Reaction** side by side on one line. **Latency**: the latency view's statistics, table of reactions and waterfall ([latency-view.md](latency-view.md), "What the page shows"). Sections are titled by a plain heading, not boxed in groups.

Main surface:

1. **Conversation** — `conversation_panel(TranscriptLog(wica, display_entry), height=CONVERSATION_HEIGHT)`, 640 px tall (the contrib's default, 420, showed too few reactions). Each closed `speech_input` shows on the input side as `🗣️ "text"`; each reasoning step is a collapsible **💬 reaction** group whose outputs are labelled by channel — **🗣️ say** (what the person heard; the hook titles the `say` execution by channel and shows the spoken text as the body), **💭 private text** (what the model wrote outside its tag, never heard), 🦾 other commands, **🚫 noop** (a reaction the model declined with `<noop/>`). Every Command item shows its **execution state live** — a spinner while it runs, then ✅ complete / ❌ failed / ⏹ cancelled with result and duration — so a `say` is visibly *in flight* for the real duration of the speech.
2. **ASR.** The speech pipeline made visible: the **ASR status** (`AsrBridge.status()`: running, dictating and which mode, and a `⚠️ capture:` tail when the embodiment reports a `mic_error`); the **voice activity** line, whether the engine's VAD hears speech right now (`status()["vad"]` — [asr-bridge.md](asr-bridge.md): `🟢 speech detected`, `⚪ no speech`, `⚠️ VAD failed` when everything passes ungated, or `— no VAD` for a recognizer that ends utterances itself), on the same timer; the **live segment text** (`AsrBridge.display_text`); a **"Stop dictation"** button. The **typed-text box** (always visible) and its **Send** button sit under the camera, beside the Conversation.
3. **Camera and Vision.** What the body sees and knows. The **Vision** section opens with the **pipeline's readout** (`tick_vision`, on the ASR's timer), a few lines rather than one long line, so they read at a glance: first the camera feed's achieved rate (the robot's daemon-paced feed, or the paced webcam) and each stage's achieved rate next to its configured one, as a short list; then, under a `Hand signs` subheading, whether the gesture input runs and its cap, and a table with one row per hand slot — the hand's raw top label and score, and its last delivered sign; then a `⚠️ camera:` / `⚠️ error:` line of its own when the camera feed reports a failure or has stalled, or a stage errored — `_Vision off._` without a `GestureInput`; the body's **camera** from `embodiment.view()` ([embodiment.md](embodiment.md), "`view()` is display-ready") shows its frame as an image beside the Conversation, mirrored like a selfie, and the body's `status` Markdown follows the Vision line — on the computer the webcam (vision on), on the robot its camera with each detected face boxed and labelled `#<id>`, the head line and the users table ([reachy-embodiment.md](reachy-embodiment.md), "The page view"). `tick_view` polls the view on a `gr.Timer` of its own (0.2 s); with no body, or a frame not there yet, the image is empty and a one-line note in the Vision section says why (`_No body._`, `_No camera frame yet._` — the computer's webcam exists only with vision on). When vision is on, the section ends with the hand demo's **snapshot controls** (the folder box on one line, **Save detector snapshot** / **Save classifier snapshot** on the next, a status line) — [gesture-input.md](gesture-input.md), "`GestureInput`".

Debug surface (behind the toggle, at the bottom):

4. **World state (live)** — `world_state_panel(wica.world)`. With no agent there is no World; the panel's place holds a one-line note.
5. **Reaction** — `reaction_panel(ReactionLog(wica, display_entry))`: every reasoning step, auto-snapping to the newest, with **Prompt** and **Instrumentation** tabs.

**The `display_entry` hook** is the one place the app injects persona knowledge into the generic panels: `speech_input` → `🗣️ "<text>"`; `hand_gesture_<n>` → `✋ hand <n>: <sign>` / `✋ hand <n>: no sign`; a `say` execution → title `🗣️ say`, body the spoken `text`; anything else → `None` (the contrib's generic default). It is the person-facing counterpart of the `speech_input` `serialize_fn` in `system.py`, and the *same* hook goes to both presenters so transcript items and reaction labels agree. Nothing in it is embodiment-specific: an embodiment's entries are labelled by the `display_fn` each `InputEntry` carries, which `entry_display(system)` composes in front of `display_entry` — the hook a session hands its presenters (on the robot, `👤` the event, `👥` who is present, `📏` the personal space, `🎯` whom the head follows).

**Refresh cost.** Each contrib panel owns its own `gr.Timer` (0.2 s) and pushes only what changed (the transcript on a change signature, the Reaction panel on a new step, the World table whole each tick). The app owns three timers: the latency view's (it sends a part only when it changed, and reads its tab's parts only while that tab is open), the ASR panel's (it reads the bridge and the gesture input) and the camera's (`view()`, a frame encoded per tick — kept apart so an image never delays the live text). The debug toggle is **visibility only** — a hidden World panel keeps ticking; a shared/injectable timer is the contrib's deferral, not this app's.

**The banner.** When a running session's `system.missing` is non-empty, its surfaces open with a banner listing the lines and a generic explanation: the session runs, typed text drives the agent wherever it was built, and what each line means for the embodiment at hand (no body ⇒ nothing to speak or move through; a body with no voice ⇒ `say` stays wired and reports a TTS error — [embodiment.md](embodiment.md)). The shared page carries no body-specific wording: an offline-development hint is part of the embodiment's own error message (the robot appends `reachy.backend = "fake"` / `"sim"` to a failed connection — [reachy-embodiment.md](reachy-embodiment.md)), which the banner shows verbatim.

## Typed-text input

A text box in the ASR panel, **always visible**, is the app's keyboard hatch into the agent. Submitting it writes the text to `speech_input` exactly as a closed ASR segment would — the *same* World update, so it flows through the identical reason → say/act → sink path and shows in the transcript as ordinary speech. It needs neither the ASR engine nor an ASR key, so it is the path by which the app stays useful with only the agent key set. It does **not** go through `AsrBridge`; it calls the funnel directly. One difference from a closed segment: an **empty/whitespace typed line is ignored** — that guard belongs to the typed path alone and never gates ASR finals. It shares the one-call-at-a-time limit with spoken input.

## The input funnel: `_deliver_speech` / `submit_speech`

Both ways in write `speech_input` through one guarded World write, built by `build_system` as two closures over the agent — the only code that writes `speech_input`, so the paths cannot drift:

- **`_deliver_speech(text)`** — the ASR path, wired as the bridge's `on_final_segment`: writes the transcript **verbatim**, empty included, a `DictatedPassage` kept as one (the prompt renders `""` as `You hear someone say: ""`, while `None` — nothing said yet, or expired — renders nothing at all; see "Inputs are transient"). Guarded on a running agent — `world.update` raises while stopped, so input before `start()` or after teardown, or with no agent, is dropped, not raised.
- **`submit_speech(text)`** — the typed path, exposed as `AppSystem.submit_speech`: strips, drops empty, then `_deliver_speech`.

`speech_input` is registered with `triggers_llm_call=True` and no trigger condition, so repeating the same text triggers again.

## Wiring and lifecycle

A session's composition follows the demo's **build → presenters → wire → start**, then **close**, the order WICA's output-wiring setter exists for (`Wica.init` takes no application callables; `set_output_command` comes afterwards, before `start()`, since it recomposes the system prompt — `wica-framework/specs/wica.md`). The presenters come before `start()` because they subscribe to the agent's Events as they are built, so they see the first reaction. The page is built once, around the session object, and outlives every session. Nothing is bound late and nothing back-patched: every object is built after the ones it needs, and everything is wired before `start()`.

**0. The entry point — `run_app(app, load, embodiment, ensure_persona)`.** Each embodiment's `main()` calls `run_app` with its `App` ([setup.md](setup.md)), its `load_config`, its embodiment's constructor (no I/O in it) and its `ensure_persona`. `run_app`:

1. parses the command line: `--folder` (default `default_folder(app.name)`), `--host` (default `127.0.0.1`), `--port`, and `--start` / `--no-start` (`app_setup.autostart.add_start_arguments`). There is no `--config`: the app runs from its folder;
2. builds the `Session` over `open_session` bound to this embodiment (below), then the `AppModel(app, ConfigFolder(folder, app.default_config), locked=session.locked)` — which creates the folder, writes the default config into an empty one and loads the folder's `.env` — then calls `ensure_persona(model.path)`;
3. when `starts_at_launch(model, options.start)`, calls `session.start(model)`; reasons it did not start are logged, and shown on the page;
4. builds the page (`build_page(model, session, open_on=…)`, step 2) and serves it, inside a `try` whose `finally` calls `session.stop()`.

**`open_session(used_config, folder)`** is one session, in order: `load(used_config, base_dir=folder)` ([configuration.md](configuration.md), "Loading"), the embodiment constructed from it, `build_system` (step 1), the presenters (`TranscriptLog` and `ReactionLog` over `entry_display(system)`), `wire` (step 3), `_start` (step 4); it returns the `Running` the page reads ([session.md](session.md)). A raise at any step after the build closes what was built (`close_session`, step 4) before it propagates: `build_system` has already entered the embodiment (a robot session, a daemon the bridge spawned), which must be exited whatever fails next.

**1. Build — `build_system(config: AppConfig, embodiment: Embodiment, *, asr_engine_factory=…, gesture_models=None) -> AppSystem`.** Gradio-free; builds and *enters* the system but wires no output and starts nothing:

1. Create the session's loop and start its thread (see "One event loop").
2. **Enter the embodiment**: `run_coroutine_threadsafe(embodiment.enter(), loop).result()`. **Any** exception degrades to *no embodiment* — `missing` gets `<display_name>: <exc>`, and the embodiment is `None` from here on (typed text still drives the agent; nothing that needs a body is built) — its `display_name` is kept on the `AppSystem` all the same, for the banner. After a successful enter, `embodiment.missing` (the per-component degrade lines gathered inside — the voice's key unset, a dependency absent, the emotion library unreadable) is appended to `missing`.
3. **Persona.** Resolve the persona **in the app** with WICA's public `resolve_system_prompt(cfg.wica.agent)` (an unreadable `system_prompt_file` raises `ConfigError` here — an `Agent: …` degrade), then append `embodiment.prompt_addendum` (when non-empty) and, when vision is enabled (and there is a body), `hand_signs_prompt_section()` from [gesture_input.py](../src/wica_interaction/gesture_input.py); derive the config WICA gets: `replace(cfg.wica, agent=replace(cfg.wica.agent, system_prompt=<persona + sections>, system_prompt_file=None))`. WICA's `resolve_system_prompt` prefers the inline prompt, so `Wica.init` never reads the file; the seeded text lands in the cached prefix.
4. **The latency view's collection**, before the agent so its first spans are seen: a `LatencyCollector`, and `install_tracing(collector)`, which installs the OpenTelemetry SDK once per process and points it at this collector; an exporter the environment asks for and cannot be had is a `Latency: …` line ([latency-view.md](latency-view.md), "Installing the SDK"). Then `Wica.init(<the derived config>, loop=loop)`, `collector.attach(wica)`, then `wica.world.register("speech_input", str, serialize_fn=…, triggers_llm_call=True, ttl=SPEECH_INPUT_TTL)`. `MissingSecretError`, any other `ConfigError`, and `ImportError` (a missing provider extra) each degrade to an `Agent: …` line — the first and the last only when Start's own check was bypassed or the environment changed since, as both are blockers ([session.md](session.md), "Start"). No sink, no output Command, no Events subscribed here.
5. Define the input funnel (above) as closures over the now-final agent.
5b. **The body's inputs**, only with an embodiment and an agent: for each of `embodiment.inputs()`, every one of its `InputEntry`s is `world.register`ed as declared, and the input is kept with a `deliver` of its own — a closure writing `world.update(key, value)` for its declared keys only (another key is logged and dropped), guarded on a running agent like `_deliver_speech`. A `ValueError` from `register` (a key the World already holds) drops that input, its entries unregistered, with a `<display_name>: …` banner line. The kept inputs, and every entry's `display_fn`, land on the `AppSystem`. Nothing is started here.
6. **Speech in**, only with an embodiment: `asr_engine_factory(cfg.asr_engine, embodiment.mic)` — by default `ASREngine(cfg, audio_source=mic)` — then `AsrBridge(engine, on_final_segment=_deliver_speech, mic_error=lambda: embodiment.mic_error, trigger_words=cfg.asr_engine.segmentation.trigger_words)` (the words `start_dictation`'s reply names — [asr-bridge.md](asr-bridge.md)). The seam is a **factory**, not a prebuilt engine, so a test's fake is built exactly where the real one is — never without a body — and records the source it was handed: the hand-off that decides whether the robot listens through its own echo-cancelled mic is asserted, not assumed. A `ValueError` (the ASR key unset, a bad module) or an `ImportError` (the provider's extra not installed) degrades to `ASR: …`. Built **after** WICA so the callback resolves against a live agent with no placeholder.
7. **Vision in**, only with `vision.enabled`, an embodiment and an agent: for each `n` in `1 … max_hands`, register `hand_gesture_<n>` (`serialize_fn=…`, `triggers_llm_call=True`, `trigger_condition_fn=sign_shown`, `ttl=HAND_GESTURE_TTL`), then `GestureInput(embodiment.camera(fps=cfg.vision.fps), on_gesture=…, threshold=…, fps=…, max_hands=…, hold_s=…, release_hold_s=…, device=…, models=gesture_models)`, whose callback writes `hand_gesture_<hand>` guarded on a running agent. Construction loads no model and opens no camera; a failure is still caught into `Vision: …`. (The persona was seeded in step 3, before this could fail: a construction failure — a programming or config error, since nothing is loaded here — leaves the "Hand signs" section in the prompt with the `Vision: …` banner line as the signal, the same as a model that fails to load after start.)

The returned `AppSystem` is a frozen snapshot: `loop` (with its thread), `display_name`, `embodiment` (or `None`), `wica`, `bridge`, `gesture`, `inputs` (the body's registered inputs, each with its `deliver`), `input_displays` (key → `display_fn`), `missing`, `submit_speech`, and `latency` (the collector; `None` without an agent). Any component that failed to build is `None` with its reason in `missing`.

**2. The page — `build_page(model, session, *, open_on) -> gr.Blocks`.** Built once per process, before or after a session starts: the heading, the four tabs, the session bar and its handlers (`session.start(model)`, `session.stop()`), app-setup's two panels, and the `gr.render` that draws the session's surfaces from `session.current` ("What the user sees"). It owns no presenter and wires nothing into the agent: a render reads the running session's `transcript` and `reactions`, lays out the contrib panels over them, and its input widgets only touch `system.submit_speech` / the bridge. What a render builds for itself is per browser tab and per draw (the latency panel's selection, the timers).

**3. Wire — `wire(system)`.** Gradio-free. On the agent: `wica.set_output_command(embodiment.voice)` when the embodiment exists and its `voice` is not `None` (setting it recomposes the system prompt to teach the `<say>` tag, hence before `start()`; with no voice no tag is taught and all the model's text is private); `register_command` for `start_dictation` / `stop_dictation` (when the bridge exists) and for each of `embodiment.commands()`. A no-op without an agent.

**4. Start and close.** `_start(system)`: `wica.start()`, then `asr_bridge.start()` scheduled onto the loop and awaited (only with an agent — there is nothing else to consume speech), then `gesture.start()` (synchronous — the vision pipeline is threads, sampling the embodiment's camera feed), then each input's `start(deliver)` scheduled onto the loop and awaited (only with an agent; one that raises is logged and stays silent, the next still starts). **`close_session(system)`** is the teardown, run by `Session.stop()` on the thread that asked for it (a Gradio worker, or the main thread at exit — never from a sink, Command or Event subscriber, which run on the loop): `wica.close()`, then each input's `stop()` on the loop (before the body exits: what a producer reads is the body's), then `gesture.stop()` (a synchronous join, **before** the embodiment exits — the robot's camera feed is the session's and resets at exit, so the stages are joined while it is live), then — only if `asr_bridge.status()["running"]` — `asr_bridge.stop()` on the loop (so the mic pump is cancelled while its stream is still valid), then `embodiment.exit()` on the loop, then the loop: stopped, its thread joined, the loop closed. Each step runs **in isolation**, each loop hop bounded by a 5 s timeout, the thread's join included: a step that raises or hangs is logged and the rest still run, so one failure cannot strand a media session or the loop thread. After it, nothing of the session is left in the process ([session.md](session.md), "Stop").

The ordering rules this obeys, all from the contrib's contract: presenters after `Wica.init`; sink, output Command and Commands wired **before `start()`**; `world.update()` works only while running; one `display_entry` hook for both presenters.

**One event loop per session — the app owns it; WICA and the embodiment adopt it.** Each session has its own loop, created by its `build_system` and closed by its `close_session`, so a session leaves no task, no thread and no half-closed transport to the next one. Within a session, a single asyncio loop runs the Agent, the ASR engine, and the embodiment's async verbs (`say`, the robot api, the mic pump). This is not optional: the `ASREngine` binds `asyncio.get_running_loop()` when it starts, and `say` and the action Commands run there as Commands. **`Wica` exposes no public accessor for the loop it creates**, so the app *owns* it — `asyncio.new_event_loop()` run in a thread it keeps and joins — and injects it as `Wica.init(…, loop=loop)`; WICA adopts it and spawns no loop thread of its own. Coroutines are scheduled onto it with `run_coroutine_threadsafe` from the main/Gradio thread: `embodiment.enter()` and `asr_bridge.start()` at startup, `stop_dictation()` from the Stop button, `asr_bridge.stop()` / `embodiment.exit()` at teardown. The ASR callback runs on that loop and calls `world.update`, thread-safe and with no cross-loop hazard.

## Degraded start

**Before a session is built**, what can be known is checked and refused: a config a section's owner would reject, an extra not installed, a key not set, a file the config names that is not there are **blockers** — Start shows them and builds nothing, and the Setup tab is where each is fixed ([session.md](session.md), "Start").

**While it is built**, like the WICA demo, a session **starts even when something could not be built** and says what, rather than failing whole: what only a real start can tell. Every such failure lands as one line in `AppSystem.missing`, shown in the session's banner; the surviving components still work (typed text reaches the agent whenever the agent built). Nothing contacts a model, ASR or TTS provider, or a robot, without its prerequisite in place.

| Failure | Raised as | Caught in | Effect |
|---|---|---|---|
| A document a loader refuses although the checks passed, or any other raise while opening the session | `ValueError`, or any exception, from `open_session` | `Session.start` | No session: what was built is closed, the reason shows on the session bar. |
| The body unavailable (the robot cannot be connected) | any exception from `embodiment.enter()` | `build_system` | `embodiment = None`, banner `<display_name>: …`; no voice, no action Commands, no ASR bridge, no gesture input. |
| A component of the body (voice key unset, provider extra missing, any other voice build failure, audio-processing dependency absent, emotions unreadable) | recorded in `embodiment.missing` by `enter()` | merged by `build_system` | That member degrades (`say` stays wired and reports the TTS error, `prompt_addendum` empty, `mic` raw); the rest of the body is up. |
| Agent key not under its variable (unset since the check) | WICA `MissingSecretError` at `Wica.init` | `build_system` | `wica = None`; banner carries WICA's message, which names the variable. The presenters are built over `None` (empty, nothing subscribed); the World panel's place shows a note; `wire` is a no-op; ASR capture is not started. |
| Agent prompt file unreadable, or any other WICA config error | WICA `ConfigError` (from the app's own `resolve_system_prompt` call, or `Wica.init`) | `build_system` | `wica = None`; banner carries WICA's message. |
| Configured agent provider's extra not installed | `ImportError` at `Wica.init` | `build_system` | `wica = None`; banner says what to install. |
| ASR key env var unset / module misconfigured / provider extra missing | `ValueError` / `ImportError` at `ASREngine(...)` | `build_system` | `bridge = None`; the ASR panel shows "stopped"; typed text remains the way in. |
| Vision misconfigured at build | any exception constructing `GestureInput` | `build_system` | `gesture = None`, banner `Vision: …`. A model that fails to load *after* start shows on the Vision line's `⚠️ error:` tail instead. |

## Testing

Fast, deterministic, no browser/mic/camera/network/robot ([testing.md](testing.md)). The lifecycle tests in `tests/test_system.py` stand a session up through the same Gradio-free steps `open_session` uses — `build_system(config, FakeEmbodiment(...), asr_engine_factory=asr_factory(FakeASREngine(...)))`, then a `TranscriptLog` (and, where a test reads prompts, a `ReactionLog`), then `wire(system)`, then `_start` — against WICA's scripted `fake` provider, and assert on the embodiment's recorded side effects (a `<say>` tag's body reaching its voice, a registered command routing back to it), on the presenters' `snapshot()`s (the transcript's input items, the 💭 item carrying the text outside the tag, a step's prompt carrying the addendum and the hand-signs section, an embodiment input's delivery reaching the prompt and waking the agent as its entry says), and on the degrade and teardown paths ([embodiment.md](embodiment.md), "Testing") — `open_session` included: a raise while building the presenters, while wiring, or while starting each still exits the body, and `close_session` leaves the loop closed and its thread joined. `run_app` is driven with the page's serving stubbed: a new folder gets the default config and the persona; `--no-start` starts nothing; a session started at launch is stopped when serving returns or raises. The start/stop cycle is `tests/test_session.py`'s ([session.md](session.md)). `build_page` is not driven in a browser; `tests/test_app_ui.py` covers `display_entry` and its composition with an embodiment's `display_fn`s (`entry_display`), the ASR status line, the Vision line, the session bar's text and button states for each status and with reasons, and that the page builds over a stopped and over a running session. The three contrib panels are tested in WICA's own suite, the Setup and Secrets panels in app-setup's.

## Out of scope (v1)

- **Barge-in:** *talking over* the agent is handled only as a reaction — WICA drops a trigger only while a **model call** is in flight; `say` runs as a detached output, so speech that closes while `say` is *playing* starts a new step with the running `say` visible in the World, and the first is cut off only if that step speaks (or cancels it). (The mic hearing the app's *own* voice *is* handled, per embodiment.)
- **A word-by-word reveal on the page:** the voice streams, but the transcript shows a `say` item once its text is complete.
- **Persistence:** the World starts empty at each session.
