# Adopt the bridge's `ReachyMiniConfig` and entered-only robot lifecycle

**Status:** Done

**Depends on** the bridge plan [202609141800_degradable-default-voice.md](../../reachy-mini-bridge/plans/202609141800_degradable-default-voice.md) being `Done` (installed editable, so no version bump): it makes a `tts` block whose synthesizer cannot be built degrade to "no voice" with `api.synthesizer_error` exposing the cause, which is what lets this app stop building the synthesizer itself.

Catches up with `reachy-mini-bridge` commit `bba5b5a` ("Add ReachyMiniConfig and a bridge-owned sim daemon lifecycle"): the bridge now owns a full declarative config (`ReachyMiniConfig`, [config.md](../../reachy-mini-bridge/specs/config.md)) with its own `from_dict` loader — including the voice's tts-engine block — `ReachyMiniApi` is constructed from that config, and the robot is built/connected only on `__aenter__` (never at construction). Implements the resulting changes to `specs/configuration.md` (the composed file becomes `wica` + `asr` + `reachy`, the voice living at `reachy.tts`) and `specs/app.md` (robot build step, TTS degrade path, wording), and repairs the 8 `tests/test_robot_control.py` failures the lifecycle change already causes. Deliberately leaves out any use of the bridge's `tools.md` layer and any change to how speech-in/out ride the api.

## What changed in the bridge (facts this plan rests on)

- `ReachyMiniConfig` (`reachy_mini_bridge.config`): `backend` + `robot` (upstream `ReachyMini(...)` kwargs, keys validated against upstream's signature) + `daemon` (`spawn` never/auto/always, `headless`, `scene`, `preload_datasets`, `startup_timeout`) + `tts` (a tts-engine `engine` block: `module` + optional, ignored `player`) + `audio.xvf3800`. `from_dict` / `from_json` / `from_json_file` trio; unknown keys rejected; errors are `reachy_mini_bridge.errors.ConfigError`, a `ValueError` subclass.
- `ReachyMiniApi(config: ReachyMiniConfig | str = "real", *, synthesizer=None)`. The bare-string shorthand still works, which is why the app still builds today. The `tts` block is consumed at construction into a `TTSEngineSynthesizer` (whose module resolves `api_key_env` right there); after the bridge plan above, a failure to build it is recorded in `api.synthesizer_error` instead of raised, and `say` raises `BridgeError` chained to it. A missing `tts` extra stays a hard `ConfigError`.
- Construction stores the config and nothing else. `__aenter__` brings up, in order: the managed daemon (when `daemon.spawn != "never"`, `sim` only), the robot (`build_robot` + `__enter__`), the media session. `api.robot` raises `BridgeError` outside the entered window — the cause of the 8 current failures (`tests/test_robot_control.py::_control` reads `api.robot` on an un-entered api).
- Baseline on this repo against the new bridge: ruff and pyright clean, `pytest` 8 failed / 59 passed.

## Design decisions (settled with the user)

1. **The `reachy` section becomes a verbatim `ReachyMiniConfig` document, delegated to the bridge's loader.** `specs/configuration.md` already states the principle ("reusing each engine's own loader and validation rather than re-implementing it here") and only carved `reachy` out *because* the bridge had no loader. It has one now, so the app-owned `ReachyConfig` / `Backend` / `_REACHY_BACKENDS` go away and `AppConfig.reachy` is a `ReachyMiniConfig` built by `ReachyMiniConfig.from_dict(cfg.get("reachy", {}))`. Absent section ⇒ `ReachyMiniConfig()` (the `real` backend, upstream defaults, no voice). `sim` development gains the daemon lifecycle for free: `"reachy": { "backend": "sim", "daemon": { "spawn": "auto" } }` spawns (or borrows) the headless MuJoCo daemon. Open question 2 of `configuration.md` (exposing the XVF3800 profile) is thereby answered: it is `reachy.audio.xvf3800`.
2. **The voice moves under `reachy.tts`; the app's top-level `tts` section is removed.** The bridge's config path ("one block, a talking robot") is used directly instead of the app rebuilding the bridge's own adapter and passing it through `synthesizer=`. This is only possible because of the bridge plan above: with it, an unset TTS key still leaves the robot (mic, ASR, actions) up, and the app reads `api.synthesizer_error` after construction to append its `TTS: …` banner entry — preserving the "an unset TTS key degrades only `say`" contract in `specs/app.md`. An absent `reachy.tts` block is reported on the same axis (`TTS: no reachy.tts block configured`), since `say` would raise `BridgeError` anyway. `config.py` therefore no longer imports `tts_engine` at all, `AppConfig.tts_engine` disappears, and the required sections shrink to `wica` and `asr`.
3. **One robot guard stays, its wording changes.** `build_system` keeps its single broad `except` around construct + `__aenter__`, but the docstring/comments/spec no longer claim construction connects: only `__aenter__` does now (and a `daemon.spawn` failure surfaces there as a bridge `DaemonError`, still caught into the `Robot: …` banner entry). The separate synthesizer guard is deleted.
4. **Robot-control tests enter the api.** `_control()` enters the `fake` api (`run(api.__aenter__())`, exiting in a `finally` / fixture teardown) so `api.robot` is available, matching how the app itself uses the api. The `fake` backend needs no daemon, so this stays offline and fast.
5. **Config loading now imports `reachy_mini`.** `ReachyMiniConfig.from_dict` validates `robot` keys against upstream's signature via a lazy import (about 0.7 s cold). `load_config` stays free of env-var and file side effects; this is noted in `configuration.md` rather than worked around, since the app imports `reachy_mini` on startup anyway.
6. **The direct `tts-engine` dependency is dropped.** Nothing in `src/` or `tests/` imports `tts_engine` any more; `reachy-mini-bridge[tts]` pulls it. The `[tool.uv.sources]` entry for it stays (harmless, and the bridge's path dependency on tts-engine resolves through it in this lock) — verify with `uv sync --dev` in step 6.
7. **The committed example targets a headful `sim` daemon** (added during implementation). `config.example.json` ships `"reachy": {"backend": "sim", "robot": {}, "daemon": {"spawn": "auto", "headless": false}, "tts": {…}, "audio": {"xvf3800": null}}` — every bridge block spelled out, so the template documents the whole section — so a fresh clone can watch the robot move in the MuJoCo viewer without touching hardware (needs `mjpython` and an unlocked GUI session). `--config` stays required: the example is a template to copy and adapt, not a config to run unmodified. `specs/app.md`, `README.md`, and the `main()` comment reword their "the example targets a real robot" rationale accordingly.
